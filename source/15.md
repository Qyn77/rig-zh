# Vector Stores & RAG

Retrieval-Augmented Generation (RAG) looks up documents relevant to a query and includes them in the prompt, grounding the model’s answer in your data. It reduces hallucinations and lets a model use information that isn’t in its training set. Rig provides the building blocks: embeddings, vector stores, and agents that retrieve context on every prompt.

Before you start

- Read [Embeddings](/docs/concepts/embeddings). RAG is built on them, and the same model must embed both documents and queries.
- Be comfortable building an [Agent](/docs/concepts/agent).
- Set `OPENAI_API_KEY` (or use another [provider client](/docs/concepts/provider_clients)).

Note

This page covers the concepts. For a guided build see the [RAG
system guide](/docs/guides/rag/rag_system), and for a specific store see
[Vector Stores](/docs/integrations/vector_stores).

## How RAG works

A RAG pipeline has two phases:

1. **Ingestion.** Split documents into chunks, embed each chunk, and store the embeddings with the chunk and its metadata in a vector store.
2. **Retrieval.** When a question arrives, embed it with the **same model**, find the nearest stored vectors (usually by cosine similarity), and put the matching chunks into the prompt.

If you are building a support bot or assistant grounded in documents you own, you want RAG. For simple classification with well-known categories, you probably don’t.

@@ANCHOR:rag-in-rig@@

## RAG in Rig

Two traits define a vector store:

- **`VectorStoreIndex`**: search for the documents closest to a query (`top_n`, `top_n_ids`).
- **`InsertDocuments`**: add embedded documents to the store.

`InMemoryVectorStore` ships with Rig and needs no external service, which makes it a good fit for development and small datasets. For production, Rig integrates with LanceDB, MongoDB, Neo4j, PostgreSQL, Qdrant, SurrealDB, and more; see [Vector Stores](/docs/integrations/vector_stores).

## Retrieved tools

An agent with many tools wastes context on tool definitions it won’t use, and large tool lists make models choose worse. Rig can store tool definitions in a vector index and send the model only the ones most relevant to each prompt, using `AgentBuilder::retrieved_tools(n, index, toolset)`. The [Tools](/docs/concepts/tools) page covers the `ToolEmbedding` trait and setup.

## Reranking

Vector search is fast but coarse. A reranking model reads the query and each candidate together and reorders them by relevance, which often improves the final context noticeably. Clients that offer reranking (Voyage AI, and OpenAI-shaped clients for endpoints that serve it) build a rerank model with `client.rerank(id)`. You call it with a `rig::operation::RerankRequest` and get back a `rig::rerank::RerankResponse` whose `results` hold each document’s original `index` and its `relevance_score`; `DynModel<rig::operation::Rerank>` is the provider-independent type:

@@ANCHOR:design-tips@@

## Design tips

- **Chunking.** Relevant information can span chunk boundaries. Overlap chunks by 10–20%, or retrieve small chunks and pass their larger parent section to the model.
- **Hybrid search.** Semantic search can miss exact terms such as product codes. Combine a full-text search with vector search and merge the lists, for example with [Reciprocal Rank Fusion](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion).
- **Conflicting or stale data.** Filter by metadata, weight by recency or source authority, and re-embed documents when the source changes.
- **Memory.** The same machinery can store long-term facts and conversation summaries for [agent memory](/docs/concepts/memory).
