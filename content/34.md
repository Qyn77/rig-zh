# 将 Rig 与 LanceDB 部署到 AWS Lambda

本指南在[将 Rig 部署到 AWS Lambda](/docs/guides/deploy/blog_1_aws_lambda)的基础上，扩展为使用 [LanceDB](https://lancedb.com) 保存嵌入的 RAG Agent。LanceDB 的存储格式支持可插拔后端，因此在 Lambda 上主要需要决定使用哪个后端：S3（可选配 DynamoDB commit store）、临时 `/tmp`，还是 EFS。本指南介绍各自的取舍及部署方式，再分析云端指标。

示例 Agent 使用 OpenAI 的 `text-embedding-3-small` 和 `gpt-5.5`。**数据来源说明**：以下保留原文作者的历史测试数据；本站没有在 Rig 0.46.0 上重测，也不能据此推断本页当前模型与依赖组合的实际性能。原文与功能相当的 Python RAG Agent 比较后，报告如下：

- Rig RAG Agent：内存用量低（96MB–113MB），冷启动快且稳定（约 160ms）。
- Python RAG Agent：内存用量较高（246MB–360MB），冷启动较慢（1,900ms–2,700ms）。

## 应用场景：蒙特利尔

[`rig-montreal-lancedb`](https://github.com/garance-buricatu/rig-aws/tree/master/rig-montreal-lancedb) 应用对[蒙特利尔开放数据](https://donnees.montreal.ca)执行 RAG。蒙特利尔市政府在各项活动中产生和管理大量数据，涵盖农业、政治、交通、健康等。开放数据应用发布这些数据集，所有市民都可免费访问。我们的应用会为所有公开数据集的元数据建立索引，让用户就开放数据提问。

`loader` 将全部数据集元数据，例如名称、描述和标签，索引到 LanceDB；`app` 根据提示词对这些数据进行向量搜索。例如：

> **提示词：** 请介绍蒙特利尔的气态污染物。浓度是如何测量的？
> **应用回答：** 蒙特利尔的气态污染物浓度由空气质量监测网络 Réseau de surveillance de la qualité de l’air（RSQA）测量。该网络由位于蒙特利尔岛上的测量站组成，持续测定空气中各种污染物的浓度，并通过遥测传输数据，……

## LanceDB 概览

[**Lance**](https://github.com/lancedb/lance) 是为高性能机器学习工作负载设计的**开源列式数据格式**。

- 使用 Rust 编写。
- 原生支持存储、查询与过滤向量、深层嵌套数据，以及多模态数据，包括文本、图片、视频、点云等。
- 支持向量相似度搜索、全文搜索和 SQL。
- 通过 [Arrow](https://arrow.apache.org/overview/) 与 Parquet 等其他列式格式互操作。
- 索引与存储基于磁盘。
- 设计目标是扩展到数百 TB 的数据。

[**LanceDB**](https://lancedb.github.io/lancedb/) 是**开源向量数据库**。

- 使用 Rust 编写。
- 构建在 Lance 之上。
- 提供 Python、JavaScript 和 Rust 客户端库。
- 可以同时保存原始数据、元数据与嵌入。

@@ANCHOR:lancedb-storage-options@@

## LanceDB 的存储选项

LanceDB 底层优化的存储格式 `lance` 足够灵活，可由多种存储后端支持，例如本地 NVMe、[EBS](https://aws.amazon.com/ebs/)、[EFS](https://aws.amazon.com/efs/)、[S3](https://aws.amazon.com/s3/)，以及其他连接云端的第三方 API。

> 使用某个存储后端，只需在 LanceDB 客户端中指定对应连接字符串。

下面介绍与 AWS Lambda 兼容的几个存储选项。

@@ANCHOR:s3---object-store@@

## S3 对象存储

> 数据作为独立对象存储，所有对象处于同一层级。
> 对象由分布式哈希表（DHT）跟踪，每个对象用唯一 ID 标识。

| **对象存储的优点** | **对象存储的缺点** |
| --- | --- |
| **不受单节点限制的扩展能力**：对象可分布到多个系统，适合处理大量数据的机器学习和 AI 应用。 | **延迟较高**：通过网络上的 HTTP/HTTPS 访问远程对象存储，相比 NFS 等文件系统协议会增加开销。元数据与对象分开存储，也会增加一些检索延迟。 |
| **价格低**：存储设计简单，通常比传统文件系统更经济。 |  |
| **高可用且具备恢复能力**：较低的存储成本允许在数据中心内及跨数据中心冗余保存数据。 |  |

## Lambda 临时存储：本地文件系统

[Lambda 临时存储](https://docs.aws.amazon.com/lambda/latest/dg/configuration-ephemeral-storage.html)是**临时的，且每个执行环境独有**，不用于持久化存储。换句话说，在 Lambda 执行期间创建于临时存储上的 LanceDB 存储，不会在函数冷启动后的新环境中保留。

这个选项只适合特定场景，主要用于测试：写入与读取必须在同一进程完成，数据也只由一次 Lambda 执行读取。

## EFS 虚拟文件系统

> 面向 EC2、Lambda 等 AWS 服务的**无服务器、弹性、共享文件系统**。
> 数据会**持久化**，可在不同 Lambda 调用之间共享；原文将其与前面未配置 commit store 的 S3 方案及临时存储方案作对比。
> 支持最多 25,000 个**并发连接**。

| **EFS 的优点** | **EFS 的缺点** |
| --- | --- |
| **有状态 Lambda**：为 Lambda 挂载 EFS 后，可以读取以前和并发执行产生的信息。 | **开发时间**：云端配置更复杂。 |
| **低延迟**：Lambda 函数与 EFS 实例位于同一 **VPC**，通过 **NFS** 协议进行低延迟网络调用。 | **成本**：比 S3 更贵。 |

#### 第二部分：理解 CloudFormation 模板

这个[模板](https://github.com/garance-buricatu/rig-aws/blob/master/rig-montreal-lancedb/template.yaml)假定 AWS 账号已经具有以下资源：

1. 一个 **VPC**，至少包含位于不同可用区的两个私有子网，每个子网都能访问公网。
2. 一个用于存放 Lambda 代码的 **S3 bucket**，即第一部分创建的 bucket。

> 如果缺少这些资源，可按 AWS 的这个[教程](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-example-private-subnets-nat.html)创建基本 VPC 和子网。

**EFS 配置**

1. **挂载目标**：为 EFS 创建两个挂载目标，每个子网一个；子网在 CloudFormation 模板的 `Parameters` 部分指定。
2. **安全组**：为 EFS 设置安全组规则，允许来自 Lambda 函数安全组的 **NFS 流量**。

**Lambda 函数配置**

1. **Loader 与 App Lambda**：将 `loader` 和 `app` 两个 Lambda 函数部署到与 EFS 挂载目标相同的子网。
2. **安全组**：分配允许访问 EFS 安全组及公网的安全组。
3. **EFS 挂载**：配置 Lambda，将 EFS 目标挂载到 `/mnt/efs`。

> 全部准备就绪后，部署 CloudFormation 模板即可一次启动环境。
