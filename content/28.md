# 多 Agent 系统

随着 LLM 工作流增长，单个 Agent 如果积累了 30 多个工具、臃肿的系统提示词和多项职责，表现会开始下降：选错工具、产生幻觉、耗尽上下文窗口。解决方式是把工作分给多个各有专长的 Agent，由“管理者”Agent、你自己的 Rust 代码，或点对点消息来协调。

@@ANCHOR:do-you-need-one@@

## 你需要多 Agent 吗？

如果工作流只涉及一个领域，工具集也较集中，少于 10–15 个，改善提示词和上下文工程几乎总比管理多个 Agent 的复杂性更划算。先尝试：

- 使用结构化输出减少歧义
- 改进检索，例如优化分块、使用更相关的数据集
- 收紧约束，更清楚地定义角色

以下情况适合多 Agent 系统：

- Agent 需要 20 多个工具，并开始选错工具
- 跨领域协作，例如文档撰写与产品开发
- 单靠检索无法解决上下文窗口耗尽
- 角色委派边界清楚

如果不能明确说明为什么需要多个 Agent，就保持单 Agent 的简单设计。如何衡量和改进已构建的系统，见[可观测性](/docs/concepts/observability)。

说明

`into_tool()` 根据工作者的**名称**、**描述**和系统提示词构建工具定义，因此应通过 `AgentBuilder::name()` 和 `AgentBuilder::description()` 同时设置名称与描述。Agent 名称会成为工具名；未命名 Agent 的工具名是 `agent_tool`，所以同一管理者注册两个未命名工作者会发生冲突。给管理者足够的轮次预算（`default_max_turns`），让它能调用工作者后再回答。

## 用 Rust 编排 Agent

管理 Agent 让模型决定谁做什么。如果步骤已经确定，直接用普通 Rust 编排更省钱、更快，也更容易测试。顺序步骤只需 `.await`，独立步骤可用 `tokio::join!` 或 `futures::future::join_all` 并发执行。通用模式见[工作流](/docs/concepts/chains)。

说明

生产环境的 swarm 可以考虑 [`ractor`](https://crates.io/crates/ractor)。它是最受欢迎的 Rust Actor 框架，在该模式上提供监督和集群支持。
