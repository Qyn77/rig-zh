# 工作流

工作流把多个模型调用串联起来：先起草再编辑、先分类再路由，或把任务分发给多个 Agent，再合并它们的回答。在 Rig 中，工作流用**普通 Rust** 编写。每个 Agent 调用都是返回 `Result` 的 `async` 函数，因此可以用 `let`、`match`、循环和 `futures::join!` 来组合，无需学习工作流 DSL。

开始之前

本页以 [Agent](/docs/concepts/agent) 为基础；涉及类型化输出的部分还需要了解[结构化输出](/docs/concepts/extractors)。每种模式在 Rig 仓库的 `examples/` 目录中都有可运行的程序，各节会给出示例名称。

## Agent 还是工作流？

设计 LLM 应用时，首要决定是：*由谁控制流程*？

- **带工具的 Agent** 让模型决定调用什么工具、调用顺序以及何时停止。适合无法事先列出步骤的开放性问题。
- **工作流**由你的代码掌控：步骤、顺序和分支都用普通 Rust 表达。每一步都可以调用模型，但下一步做什么不由模型决定。适合流程已知的情况，成本更低、行为更可预测，也能逐步测试。

选择能解决问题、且自主程度最低的设计。某一步不需要模型，就写普通函数；步骤已知，就写工作流。只有需要模型判断的部分才使用 Agent 循环。两者可以自由组合：工作流中的一步可以是使用工具的 Agent，Agent 也可以把工作流当作工具调用。

## 把 Agent 当作工具

也可以反过来，让 Agent 决定何时调用另一个 Agent：`Agent::into_tool()` 将 Agent 包装为工具，接收 `prompt` 参数并返回子 Agent 的回答。完整示例见[把 Agent 当作工具](/docs/concepts/agent#agents-as-tools)，以及 `agent_with_agent_tool` 和 `multi_agent` 示例。

@@ANCHOR:handling-failures@@

## 处理失败

每一步都返回 `Result`，因此错误处理就是普通 Rust：用 `?` 中止工作流，用 `match` 回退到其他步骤，或者只重试某一步，而不重做前面的步骤。[错误处理](/docs/concepts/error_handling)介绍如何区分值得重试的临时服务商错误与永久错误。应按步骤重试，而不是在整个工作流外层重试，以免再次执行已经产生副作用的步骤。
