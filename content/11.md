# 工具（Tools）

工具让 Agent 不只生成文本：它们把你的 Rust 函数开放给模型，让模型调用函数来获取数据、执行计算或访问外部系统。模型请求工具时，Rig 会解析参数、运行你的代码、把结果传回模型，再继续循环。

开始之前

- 阅读 [智能体](/docs/concepts/agent)：工具接入 Agent，并在其多轮循环中执行。
- 配置[模型服务商客户端](/docs/concepts/provider_clients)，示例通过 `OPENAI_API_KEY` 使用 OpenAI。
- 检索工具基于[向量存储与 RAG](/docs/concepts/rag)。

## `Tool` trait

每个类型化工具都实现 [`rig::tool::Tool`](https://docs.rs/rig/0.46.0/rig/tool/trait.Tool.html)。`use rig::prelude::*;` 会将 `Tool` 和 `ToolContext` 引入作用域；本页代码片段均假设已经这样导入。

- `const NAME`：模型调用工具时使用的名称，必须在 Agent 内唯一。
- `type Args`：实现 `Deserialize` 的类型，模型的 JSON 参数会被解析为此类型。解析失败的参数不会进入你的代码；模型会收到“参数无效”的结果。
- `type Output`：成功调用的返回值。任何实现 `Serialize` 的类型都可使用，参见[工具输出](#tool-output)。
- `type Error`：你的错误类型，必须实现 `std::error::Error`。
- `description()` 和 `parameters()`：发送给服务商的说明文本和 JSON Schema。模型根据 schema 了解如何调用工具，因此应描述每个字段。
- `call(&self, ctx, args)`：实际工作逻辑。`ctx` 是本次调用的 [`ToolContext`](#tool-context)，不需要时可以忽略。
- `map_error(&self, error)`：可选。将你的错误转换为模型和钩子看到的内容，参见[工具失败时](#when-a-tool-fails)。

## `#[rig::rig_tool]` 宏

多数工具不需要手写 `impl`。在返回 `Result<T, E>` 的同步或 `async` 函数上添加 `#[rig::rig_tool]`，宏会生成：

- 按函数名转为 PascalCase 命名的单元结构体，例如 `get_weather` 变为 `GetWeather`，可传给 `.tool(...)`；
- 带有派生 JSON Schema 的参数结构体，例如 `GetWeatherParameters`；
- 工具 trait 实现，以及一个 `static GET_WEATHER: GetWeather` 实例。

@@CODE_003@@

宏接受以下选项，全部可省略：

- `name = "..."`：工具名，默认为函数名。
- `description = "..."`：工具描述，默认为函数的文档注释。
- `params(arg = "...", ...)`：参数描述。参数上的 `///` 文档注释也有效。两种方式都没提供时会生成占位描述，因此请补充描述。
- `required(arg, ...)`：模型必须提供的参数。

未指定 `required(...)` 时，所有非 `Option` 参数都必填，`Option` 参数都可选。如果显式提供 `required(...)` 列表，未列入的参数将变为可选；模型省略它们时，会使用 `Default::default()`，因此这些参数类型必须实现 `Default`。将 `Option` 参数列入 `required(...)` 会导致编译错误。

如果函数的第一个参数是 `&mut rig::tool::ToolContext`，它会收到[工具上下文](#tool-context)；上下文不会出现在模型参数里。如果以更短的路径导入 `ToolContext`，请给该参数标记 `#[rig(context)]`，让宏能识别它。

## 工具失败时

工具返回 `Err` **不会**结束运行。Rig 会将错误转为失败的工具结果，发送给模型，然后继续循环：模型可以修正参数后重试、尝试另一个工具，或向用户解释失败原因。

模型读取到什么取决于错误类型。Rig 会将每个工具错误转换为 [`ToolExecutionError`](https://docs.rs/rig/0.46.0/rig/tool/struct.ToolExecutionError.html)，它将两类文本分开：供日志和钩子使用的 **message**，以及模型读取的 **model output**。

- **任意错误类型**，例如 `io::Error`、`reqwest::Error` 或你自己的枚举，由默认 `map_error` 包装。模型只能看到笼统反馈 `the tool failed`，因此路径、主机或凭证等内部细节不会泄露到对话中。你的代码仍可通过 `error.message()` 和 `error.downcast_ref::<E>()` 访问原始错误。
- **你自行构建的 `ToolExecutionError`** 会向模型展示它的消息。可以按失败类型选择构造器：`invalid_args`、`not_found`、`permission_denied`、`timeout`、`rate_limited`、`network`、`provider`、`cancelled` 和 `other`。`refused(..)` 表示主动拒绝。

应面向模型编写这些消息：`"Division by zero; y must not be 0"`（除数为零；y 不能为 0）有助于恢复，`"error 500"` 则没有帮助。每次恢复尝试都消耗一个轮次，因此要给 `.max_turns(..)` 留出余量。

如果既要为自己的代码保留类型化错误，又要给模型提供有用消息，可以覆盖 `map_error`：

@@CODE_005@@

`with_code`、`with_retryable` 和 `with_http_status` 添加结构化信息，供[钩子](/docs/concepts/hooks)据此处理；这些信息都不会发送给模型。

还有两种失败采用不同处理方式。参数不符合 `Args` 时，会像其他工具错误一样，变成发给模型的 `invalid_args` 结果。调用不存在的工具时，运行则会返回 `PromptError::UnknownToolCall`，除非钩子进行了恢复，参见[钩子](/docs/concepts/hooks)。

## 设计好用的工具

模型通过阅读名称、描述和参数 schema 来选择工具。这些文本就是接口，大多数工具使用失败都源于这些说明，而不是模型本身。

- **使用有描述性的名称**，采用 `snake_case`，避免缩写：`search_orders` 比 `so` 更好。
- **面向模型写描述**。说明工具做什么、什么时候使用，以及什么时候*不应*使用。
- **描述每个参数**，并尽量减少参数数量、降低复杂度。相比填写嵌套对象，模型填写三个说明清楚的字符串或数字字段通常可靠得多。
- **每次请求只提供少量工具**。工具列表变长时，选择效果会下降，大致在超过十到二十个工具之后更明显。可以将大量工具分配给不同专用 Agent，或使用[检索工具](#retrieved-tools)，让每次请求只看到相关的少量工具。
- **返回精简结果**。对于大型或敏感数据，可返回由你的代码稍后解析的 ID，而不是直接返回数据本身。

## 强制工具调用

`AgentBuilder::tool_choice(ToolChoice::Required)` 会在**每一轮**强制调用工具，模型因此永远没有机会写出最终答案，运行最终会返回 `PromptError::MaxTurns`。只应将它用于单轮任务。若要只在首轮强制使用工具，然后让模型回答，应在检查 `ctx.turn()` 的钩子中设置该选项；参见[请求补丁](/docs/concepts/hooks#request-patches)和 [`force_tool_first_turn`](https://github.com/0xPlaygrounds/rig/tree/v0.46.0/examples/force_tool_first_turn) 示例。

## MCP 工具

工具不必位于你的 crate 中。[模型上下文协议](https://modelcontextprotocol.io)让 Agent 能将其他进程提供的工具，与自己的工具一起使用，例如文件系统访问、浏览器、数据库和 SaaS 集成。Rig 的 MCP 支持位于 `rig::tool::rmcp`，通过 `rmcp` feature 启用。配置方法和完整示例见[模型上下文协议](/docs/integrations/model_context_protocol)。
